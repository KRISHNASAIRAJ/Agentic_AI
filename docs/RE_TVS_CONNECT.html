01Executive summary

Four findings that change the project's direction. Every claim below is quoted from decompiled bytecode of the APK you supplied.

🍃

Carbon Confirmed

No BLE frame writes the dash's carbon screen. TVS Connect formats CO₂ with a ×0.8 factor and stores it per ride; Jupiter Connect's app-only estimate is the right architecture.

📞

Caller ID Resolved

The Jupiter branch sends one 20-byte 5B 43 frame. The famous 3-packet 1/3/2 sequence belongs to other models in the same APK.

💬

Social counters Confirmed

5B 9C is real: WhatsApp in 5 bits (≤31), Facebook in 4 bits (≤15), Instagram raw. Missed calls live in keepalive byte 10, sourced from the call log, capped at 99.

🧭

Outcome Implemented

All nine changes applied and verified — 35 JVM tests, 0 failures, debug APK builds green. Bluetooth connection behaviour was deliberately left untouched; traffic screens deferred.

Bottom line: the earlier community notes were directionally right but model-ambiguous. Decompiling the actual 8.14.3 APK resolved the caller-format conflict and turned the previously "unverified" 0x9C social frame into a confirmed feature.

Reading the evidence

Two BLE stacks coexist in this build; the scooter model selects which one runs. For the Jupiter 125 the relevant classes are:

  • com/tvs/ble/feature/utils/TelephonyUtils.java — model-specific caller branch
  • com/tvs/ble/feature/datasender/JupiterMobileToCluster.java — Jupiter keepalive
  • com/tvs/bluetooth/core/utils/{BluetoothUtil,BlePacketsProvider}.java — frame builders
  • com/tvsm/connect/bluetooth/sendreceive/N109U347N251DataSenderToCluster.java — legacy sender
  • com/tvsm/connect/bluetooth/bluetoothlegatt/SampleGattAttributes.java — data-ID table
This build is newer than the community-referenced v8.14.1; where they disagree, this APK wins.

04Carbon

The definitive answer: there is no carbon write on the wire. Both apps compute a local figure; only the cluster's internal ISS-derived value appears on the dash.

Found in TVS Connect Confirmed

convertCO2(double d) → String.valueOf(d * 0.8d)

BluetoothUtil.java:127-129 — a display formatter, not a wire encoder. co2Image() (lines 116-121) picks low/medium/high icons at ≤25 and ≤50. Realm models persist co2Saved per ride and cumulatively; analytics logs CO2_saved. No carbon data ID exists. The aptly misnamed carbonEmission(int) actually sends the 0x9C social frame.

Implemented in JupiterConnect Implemented

issSeconds × 0.5/3600 × 2.31  → preferred
(km ÷ economy) × 0.10 × 2.31  → fallback
(km ÷ 3) × 25 × 0.5/3600 × 2.31 → distance-only

RideStore.kt:210-251. The lifetime ISS counter from inbound 0x19 is adopted as a non-decreasing floor by foldIssDuration(). The result is shown in the app only and synced to Supabase as carbon_seconds.

05Caller ID & message formats

The conflict between "one frame" and "three packets" is resolved by model: the Jupiter branch in this APK uses a single frame.

Jupiter caller frame — 20 bytes Resolved

0x5B · 0x43 · UTF-8 name (or number, +91 stripped) · 0x00 pad · 0xFF

Built by TelephonyUtils.writeJupiterCallerInformationToCluster() (lines 315-326) using createMobileToClusterArray(name, (byte)67). The legacy createCallerNameArray() produces the same 20-byte shape.

Generic 3-packet sequence — 21 bytes Other models

0x5B · 0x43 · subId (1 = number, 3 = country code, 2 = name) · text · 0xFF

TelephonyUtils.writeCallerInformationToCluster() (lines 269-283) → BlePacketsProvider.returnContactInfoPacket() (lines 437-455). Present in the APK, but not on the Jupiter path.

06Social counters

Both counter channels are confirmed in the APK. JupiterConnect has the right frame IDs but needs corrections to the counter semantics.

Keepalive 5B 4A — missed calls at byte 10 Confirmed

2 = signal/battery · 4 = ambient+40 · 6-9 = 12-hour clock (AP = AM/PM) · 10 = missed calls (MC) · 11 = network type · 12-14 = date · 19 = FF

BluetoothUtil.getMissedCalls() (698-731) reads the Android call log with type=3 AND is_read=0, requires READ_CALL_LOG, and caps at 99. The Jupiter stack stores that value in the TVSM / MISSED_CALL preference and sends it in byte 10 on every keepalive.

Social frame 5B 9C — three unread counters Confirmed

2 = WhatsApp (low 5 bits, ≤31) · 3 = Facebook (low 4 bits, ≤15) · 4 = Instagram (raw byte) · 5 = delivery alert · 10 = alert/carbon param · 19 = FF

Built by sendMobileDataNotificationAndAlert() (1542-1568). Counts come from SocialMediaCountHelper, which increments per notification, stores a JSON blob under SocialMediaCount, and exposes clearRecords().

Decisions — resolved

  • C3: approved — READ_CALL_LOG added; missed calls read from the call log, capped at 99.
  • C2: approved — Facebook / Instagram triggers wired, counters clamped to 31 / 15, and a "Clear social counters" control added.
  • C5: keep sending 0x53 until a dash capture settles whether the card renders.
  • C6: skipped — connection-related behaviour untouched.

Deferred — traffic screens

The APK contains the traffic-screen builders (weather 0x5D, cricket 0x81, football 0x91, news 0x96), but their content is fetched from TVS cloud APIs. Free-API replacement is feasible: a Nifty/Sensex screen should use the generic 17-byte text rows (0x4C/0x63) rather than the football frame, which the cluster renders as a sports scoreboard. Separate feature, pending a plan.

09Verification checklist — needs the scooter

Static analysis can settle frame layout. Only bytes off the wire or a photograph of the dash can settle rendering.

  • Capture an incoming call; confirm the Jupiter cluster renders the single 5B 43 frame (keep the 3-packet sequence as A/B fallback).
  • Confirm keepalive byte 10 against a known number of unread missed calls (cap 99).
  • Send a 5B 9C frame with known WhatsApp / Facebook / Instagram values and photograph the Social screen; verify the 31 / 15 caps.
  • Check whether 0x53 produces any card on the Jupiter 125.
  • Verify that no outbound frame requires a checksum at byte 18.
  • Confirm how many of the 17 payload characters are actually visible on each text row.
